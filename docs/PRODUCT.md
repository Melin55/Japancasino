# HPいい感じにしますくん：企画・実装仕様

更新日：2026-10-31（日本時間）。判断原則は [SHIBATA_PRODUCT_HARNESS.md](SHIBATA_PRODUCT_HARNESS.md)。ユーザーの最新指示と案件条件を優先する。

## 利用者と価値

初期対象は、既存の企業サイトがあり、問い合わせや会社の魅力を改善したい経営者・担当者。制作の専門用語を知らなくても、URLと10件の採点から、情報を保持したリニューアル案を比較・確認できることを目指す。初期実装は公開HTMLを最大12ページ扱う。EC、会員機能、業務システムの移植は対象外。

主要操作は URL入力 → 公開情報の調査 → 出典付きの自社・競合整理 → 10件の参考デザインを1〜5点で採点 → 採点に基づく仮サイト → 保持検査 → ZIP取得・採否記録。現在のサイトは書き換えない。

## 成果指標と完了条件

製品価値の指標は「担当者が採用したいと判断する提案の割合」「必要な手直し時間」「再生成で同じ指摘が減るか」。採点完了率・初回提案までの時間・API費用は工程指標。公開後の有効問い合わせや予約、検索流入、AI引用は別の成果指標とし、所有者の好みと混同しない。

MVPの完了は、実URLでの出典確認、10件の実在参考先、全採点の保存と反映、複数ページの仮サイト、保持検査、主要操作の実行を確認した時点。サンプルだけの成功では完了扱いにしない。

## 実装の境界

- URLと任意の目的を入力。最大12ページの公開HTMLと1つの sitemap.xml を読み、本文・リンク・パンくず・画像・タイトル・description・canonical・アンカーを記録する。robots.txtを尊重する。
- JavaScriptでのみ表示される本文、PDF、ログイン内、フォーム動作、決済、サイトマップ索引、クエリ付きリンクの巡回は未対応。取得範囲・エラー・未巡回件数をレポートに残す。
- OpenAI Responses APIのweb_searchと構造化出力で、事業、評判、競合、参考デザイン、改善案を調査。検索が返した出典にない主張は事実扱いにせず、未検証の成長数値を破棄する。
- 「伸びている」は同一指標・期間・単位・出典がある場合に限定。観測・推定・不明を区別する。売上とアクセスの成長は混同しない。外部データのライセンス契約や時系列の自動取得は未実装。
- 本番の参考先は異なる10ドメイン。HTTPで到達性を確認し、失敗時は明示する。スクリーンショットには公開URLをWordPress mShotsへ送る。取得失敗は原サイトリンクへ誘導する。写真・色の特徴は現在AIの仮分類であり、画像認識による実測値ではない。
- 採点は1〜5点、任意の理由、戻る操作、1〜5キー、左右スワイプ（1点・5点）に対応。途中の値をサーバー保存する。
- 好みは5つの少数の特徴で推定。平均点からの偏差で重み付けし、同点ばかりの場合は信号なしとして中立のデザインにする。学習済みモデルとは呼ばない。
- AIは既存ブロックIDの並べ替えと改善案を返し、HTMLは制約付きのレンダラーが生成する。未知のIDは採用せず、AIが省いた既存本文は補完する。新たな実績・価格・企業情報を本文に捏造しない。
- 配色、文字、余白、見出しの大きさを採点に応じて変える。修正コメントは次回の構成検討にも渡す。サンプルでは「文字を大きく」の修正反映を検証する。
- 保持検査は生成されたHTMLを再解析し、本文の一致、リンク、パンくずの表示とJSON-LD、メタ情報、アンカーを確認する。検査の合格は取得した範囲の保証であり、取得漏れまで解消したという意味ではない。
- ZIPはページごとのHTML、URL対応表、提案・検査結果を含む。確認用のnoindexを維持する。公開時のDNS・CMS移行・リダイレクト設定は未実装。

## 費用・運用

まず契約済みのOpenAIキーを再利用し、専用の交通量API・検索API・スクリーンショット有料サービスは追加しない。Node.jsと4つの小さなライブラリで実装。専用モデル訓練は行わない。

通常は調査1回、提案1回のモデル呼び出し。検索ツール呼び出しは最大6回、出力上限は調査14,000・提案9,000トークン、入力は140,000文字以内。自動リトライはしない。提案再生成は1案件3回まで、作成は同一ブラウザーで1時間6回まで。これは開発用の簡易制限であり、公開サービスの課金・不正利用対策を代替しない。usageを段階別に記録する。実額は契約・モデル・検索単価で変わり、現在は未計測。

`.data/`にローカル保存し、利用者の削除操作で除去する。現状はCookieに紐づく開発用の単一インスタンスで、Cookieを失うと再開できない。認証・チーム共有・自動保管期限は本番提供前の課題。生のAPIキーはサーバー環境からのみ参照し、ブラウザー・ログ・Gitに渡さない。

## 原則の反映

| 原則 | 今回の反映と確認 |
|---|---|
| 1 実際の成果 | ブラウザーで採点・生成・検査・ZIP・コメント・再開まで操作。実AI確認は未実施と区別 |
| 2 顧客と価値 | 既存企業サイトの担当者、情報保持と提案の採用判断を中心に設定 |
| 3 認知負担 | URL、目的、5点評価。PC/スマホ、キー操作、戻る、再開 |
| 4 調査を仕様へ | Tasteなどとの差分から保持検査・根拠・採否記録を実装。成長不明を明示 |
| 5 改善と証拠 | 採点と採否をイベント保存。コメントを再生成へ渡す。保存だけを学習と称さない |
| 6 費用対効果 | 既存キー、既存OSS、呼び出し上限、usage記録。追加契約なし |
| 7 品質 | PC/スマホの実画面、保持検査、主要操作のテスト。架空データをサンプルと明示 |
| 8 個別最適 | 評価・理由・修正コメントに基づく範囲のみ反映 |
| 9 小さく実用化 | まず公開HTMLの企業サイト。既存の検索・生成基盤を組み合わせる |

## 残るプロダクト仮説

10件で十分な好みの信号が得られるか、企業情報保持が提案採用率を上げるか、既存製品より修正時間が減るかは未検証。「上位互換」を事実として販売しない。候補の後半4件を適応選択する方式も未実装で、固定10件との比較後に導入する。
